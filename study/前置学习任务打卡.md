## A类问题（没用过推理框架 / 原理不熟）

### A1: 模型、Tokenizer、推理框架、GPU、API 服务之间的关系

```
用户请求 → API 服务 → 推理框架 → Tokenizer（编解码）
                              ↓
                           GPU（计算）
                              ↓
                         模型（Forward）
```

- **Tokenizer**：将文本转为 token ID，或将 token 转回文本
- **模型**：神经网络权重，负责 token 序列的 forward 计算
- **推理框架**：管理模型加载、请求调度、KV Cache、Attention 计算等
- **GPU**：提供算力，执行矩阵乘、Attention 等 CUDA kernel
- **API 服务**：暴露 HTTP 接口，接收请求、返回响应

---

### A2: Prefill 和 Decode 阶段的计算特性

| 阶段 | 计算特性 | 原因 |
|------|----------|------|
| **Prefill** | **计算密集** | 首次 forward 处理整个输入 prompt，需完成全部 attention 计算，计算量大但可并行 |
| **Decode** | **带宽密集** | 逐 token 生成，每次只做一次 small 矩阵乘，瓶颈在模型权重和 KV Cache 的读取带宽 |

---

### A3: TTFT 和 TPOT 分别对应哪个阶段

| 指标 | 全称 | 对应阶段 | 含义 |
|------|------|----------|------|
| **TTFT** | Time To First Token | Prefill | 从请求到输出第一个 token 的延迟 |
| **TPOT** | Time Per Output Token | Decode | 生成每个输出 token 的平均时间 |

---

## B类问题（用过 vLLM，没用过 SGLang）

### B1: RadixAttention 与 PagedAttention 的异同

| 维度 | RadixAttention (SGLang) | PagedAttention (vLLM) |
|------|-------------------------|----------------------|
| **设计目标** | 复用共享前缀的 KV Cache | 管理非连续物理块的 KV Cache |
| **数据结构** | Radix Tree（前缀树） | 链表 + 物理块映射 |
| **共享前缀** | 支持，多请求共享同一前缀的 KV Cache | 不直接支持共享前缀 |
| **适用场景** | System Prompt、few-shot learning | 单请求内的 block 管理 |
| **实现复杂度** | 较高 | 较低 |

**相同点**：都旨在高效管理 KV Cache，减少内存碎片

---

### B2: vLLM 与 SGLang 对比表

| 维度 | vLLM | SGLang |
|------|------|--------|
| **调度** | Continuous Batching | RadixAttention +断续 Batch |
| **KV Cache** | PagedAttention | RadixAttention |
| **Attention 后端** | FlashAttention 等 | FlashInfer, FlashDecoding, TRITON_ATTN |
| **API** | OpenAI 兼容 | OpenAI 兼容 + 扩展 |
| **模型支持** | 广泛（HuggingFace、ChatGLM等） | 广泛 + DeepSeek 优化 |
| **硬件支持** | NVIDIA GPU | NVIDIA GPU + 国产卡 |
| **量化** | AWQ, GPTQ, FP8 | AWQ, GPTQ, FP8 |
| **部署复杂度** | 简单 | 中等（功能更多） |

---

### B3: Qwen / DeepSeek 支持版本和环境要求

| 模型 | vLLM | SGLang |
|------|------|--------|
| **Qwen** | 0.3+ 支持 Qwen2/Qwen3 | 支持，需对应 SGLang 版本 |
| **DeepSeek** | vLLM 0.4+ 支持 V2/V3 | SGLang 0.4+ 支持 |

**环境要求**：均需要 CUDA 12.1+，建议 A100/H100 等大显存 GPU

---

> 需执行：`nvidia-smi`、`nvcc --version`、`python --version`、`docker --version`

## C类问题（用过 SGLang，想深入 mini-sglang）

### C1: 阅读 mini-sglang README 和目录结构

**项目定位**：
- mini-sglang 是 SGLang 的精简版，约 5000 行 Python 代码
- 既是高性能推理引擎，也是教学/研究参考实现

**核心特性**：
- Radix Cache：共享前缀的 KV 缓存复用
- Chunked Prefill：减少长上下文峰值内存
- Overlap Scheduling：CPU 调度与 GPU 计算 overlap
- Tensor Parallelism：多卡分布式推理
- 集成 FlashAttention 和 FlashInfer

**目录结构**：
```
python/minisgl/
├── attention/     # Attention 实现（fa.py, fi.py, trtllm.py）
├── benchmark/     # 基准测试客户端
├── distributed/   # 分布式通信（TP 实现）
├── engine/        # 核心引擎（engine, config, graph, sample）
├── kernel/        # CUDA/Triton 内核
├── kvcache/       # KV 缓存（radix_cache, mha_pool, naive_cache）
├── layers/        # 模型层（linear, attention, moe, norm, rotary）
├── llm/           # LLM 接口
├── message/       # 消息/分词器
└── models/        # 模型实现（llama, mistral）
```

---

### C2: 相比 SGLang 简化/省略的 3 个生产级能力

1. **分布式部署简化**：mini-sglang 简化了分布式通信，主要支持基础 Tensor Parallelism，缺少 SGLang 的完整多节点支持

2. **后端 Attention 简化**：仅支持 FlashAttention 和 FlashInfer 两种后端，SGLang 支持更多（FlashInfer, FlashDecoding, TRITON_ATTNs等）

3. **调度策略简化**：SGLang 实现了复杂的请求调度（断续 batch、chunked prefill 等），mini-sglang 简化了调度逻辑，聚焦核心机制

---

### C3: 重点实现的 3 个核心机制

1. **RadixAttention**：基于 Radix Tree 的 KV 缓存管理，支持共享前缀复用和高效树形查找

2. **Chunked Prefill**：将长序列的 prefill 分块处理，降低峰值显存占用

3. **Overlap Scheduling**：GPU 执行与 CPU 调度解耦，隐藏调度开销

---

### C4: GPU 环境准备

> 需在 Linux + CUDA 环境下按 README 安装，运行 Qwen3-0.6B 验证

## 公共问题

### 公共问题 1: SGLang 与 mini-sglang 是什么关系？

| 维度 | SGLang | mini-sglang |
|------|--------|-------------|
| 代码规模 | 完整生产级（~10万行） | 精简教学级（~5000行） |
| 依赖 | 完整生态（vLLM, TGI 等） | 最小依赖 |
| 分布式 | 多节点、多 worker | 仅单节点多卡 TP |
| 调度 | 复杂断续 batch | 简化调度 |
| Attention 后端 | 多种后端 | FlashAttention + FlashInfer |
| KV Cache | Radix + Paged | Radix（精简版） |
| HTTP 服务 | 完整 OpenAI 兼容 | 简化版 |
| 教学目的 | 否 | 是 |

**关系总结**：mini-sglang 是 SGLang 的"解剖版"，保留核心机制，去除生产级复杂性，便于学习理解。

### 公共问题 2: mini-sglang 的运行环境和最小入门模型

**运行环境**：
- OS：Linux only（x86_64 / aarch64），Windows 需 WSL2，不支持 macOS
- Python：3.10+，推荐 3.12
- GPU：NVIDIA GPU + CUDA Toolkit
- Docker：推荐

**最小入门模型**：Qwen3-0.6B（单卡，≥8GB 显存）
